# The DSL-generated stress corpus is build-time, dashlang-authored, exact-rect

    status   accepted (story #46, 2026-07-17)
    scope    crates/dashlang (builder vocabulary + the corpus test),
             corpus/dsl-generated/, docs/specification/05-qualification.md
    binds    E3 (the six-case stress corpus), R2

## Context

Story #46 builds the E3 stress corpus: the six named layout edge cases —
negative gap, hug-in-fill, wrap, grid spans, baseline, variant topology
change — green in CI, generated by `dashlang` rather than hand-built in Figma
(DESIGN_1 §6.2/§11). It depends on the engine's v0.8 layout vocabulary
(story #43) and the negative-margin-hug rebate (debt #236), both landed. E3
stays **partial** after this story: five of the six named cases are proven
exactly, and the variant case is proven as a layout-topology change but not
the Figma child-count form, which needs the variant `Visible` widening —
issue #283, the path to met (see D4).

## D1 — Build-time DSL authoring, not committed generated files

The corpus is authored through the producer surface at test time, not
serialized as committed scene files. DESIGN_1 §6.2 defines "generated" as
code-authored (components are functions, loops are repeaters), the opposite
of a Figma file — not a second serialized IR. A committed-scene-file corpus
would add an artifact to maintain and would not exercise the producer
surface the corpus exists to stress. The two pre-existing cases already
follow this shape (`corpus/dsl-generated/README.md`).

## D2 — The corpus proof lives in `crates/dashlang/tests/corpus.rs`

The crate map names `dashlang` the stress-corpus generator. The proof is a
solving-correctness proof — each scene solved by `dashscene-engine`'s
`TaffySolver` (a dev-dependency already present) and pinned against
hand-computed rects — so it needs no Skia. The hand-built pixel goldens for
wrap, grid, and baseline already exist in
`goldens/tooling/tests/v08_fidelity.rs` (story #43); the corpus is the
DSL-generated, exact-rect companion, not a duplicate image. Placing it in
`goldens/tooling` would pull in Skia for no rendering and separate the
generator's proof from the generator crate. Rejected.

Every scene is integer-dimensioned so the rect comparison is exact
(`docs/decisions/v02-flex-goldens-per-construct.md`), and rects are read
back by `NodeId` (looked up by the node's authored name), never by a
positional DFS index (debt #119).

## D3 — The builder gains the v0.8 layout vocabulary, mirroring core

`Node` gains `cross_gap`, `grid_row`, `grid_column`, `grid_row_span`,
`grid_column_span` (more `Layout`-mirroring setters) plus `grid_rows` /
`grid_columns`, whose track lists are separate `Node` fields because they
are variable-length and `Layout` is `Copy` — the same split core makes.
Each new prop stages only when authored, so a non-grid node reaches the
arena unchanged (pinned by the unset-defaults acceptance tests). This
follows the v0.2-close precedent: the flex vocabulary was folded into the
builder by the story that first needed it
(`docs/decisions/dashlang-flex-vocabulary.md`). Baseline needs no new
setter — `cross_align(CrossAxisAlign::Baseline)` already reaches the arena.

## D4 — Two cases author against core's `Txn`, not the builder

The variant and negative-gap cases are not builder vocabulary and author
against core's staged-mutation API directly:

- Variant declaration (`add_variant_set` / `set_variant`) is a core
  concept — the sparse five-prop slice `X/Y/Width/Height/Fill`
  (`docs/decisions/variant-set-flat-index.md`), not a value-tree construct.
  Extending `dashlang` with a variant authoring surface is a larger,
  separate design (how a value tree declares members and overrides) and out
  of this story's scope. The variant case exercises the topology change the
  slice can express: a `set_variant` that overrides one chip's width past
  the point where the next chip fits makes a wrap line appear, so the Hug
  container grows and the flow restructures — a resolved-layout topology
  change, never a node-tree change.

  Reported limit (review C1): the stronger reading — a child LEAVING the
  laid-out set — is a child-count change, which in this variant model means
  a member setting `Prop::Visible(false)` → `Display::None`. `Visible` is
  not in the five-prop slice, and widening it (core `VariantValue` plus the
  `dashbuf` variant table, R7 append) is out of this story's scope and
  touches `dashbuf`. That widening is its own story, issue #283; it is
  `variant-set-flat-index.md`'s named "additive future work" surfacing
  against E3, and E3 stays partial until it lands.
- Negative gap is lowered by a shared core `Txn` pass
  (`docs/decisions/negative-gap-lowering.md`), which the builder does not
  call. The DSL authors the lowered (negative-margin) form directly and a
  core `gap` + `lower_negative_gaps` form cross-checks it. A rect test
  cannot witness that the lowering ran (taffy applies a raw negative gap
  identically), so both forms are pinned to the same hand-computed rects.
  The case is a Hug container, so its width is correct only under the #236
  rebate (`docs/decisions/negative-margin-hug-rebate.md`) — a plain flex
  row, never wrap, because a negative wrap gap is a named refusal
  (`docs/decisions/v08-layout-vocabulary-shape.md` D5).

## Residual gaps, declared

- **Variant child-leaves (C1):** blocked on the variant five-prop slice — see
  D4. A child LEAVING the laid-out set under a switch needs a `Visible`
  override the vocabulary does not carry; the widening is issue #283, and E3
  stays partial until it lands (`docs/decisions/variant-set-flat-index.md`).
- **Grid zero-minimum (C7):** the grid case does not make `minmax(0, 1fr)`'s
  zero minimum load-bearing — a fraction track holding oversized content
  entangles with the open fixed-child-overflow question (issue #272), so it is
  left as a debt candidate rather than forced against uncaptured behavior.
- **Leaf baseline (#273):** a leaf's baseline is its bottom edge, not a glyph
  baseline (the measure seam carries none), disclosed at Q-4 and tracked.
